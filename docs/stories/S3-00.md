# S3-00: durable telemetry store

## Goal
S3-02 as originally written stored counters in "a small JSON or SQLite file on the deploy target". agent-cost-calc deploys to Vercel, where the function filesystem is ephemeral and per-invocation. Every increment would be lost at cold start, `runs_30d` would read near zero regardless of traffic, and the day-90 kill/scale call would be made from a fabricated number.

**Ruled 2026-09-09:** the storage choice is made here, before S3-02 builds against it, rather than left to the builder or proved by a durability AC bolted onto S3-02.

## Scope
- Read the repo's actual deploy config first and record what it is in the report (framework, host, region, existing env vars).
- Provision one durable key-value or SQL store reachable from the deploy target. Preference order: a store already present in the repo > Vercel KV > Turso > Postgres. Do not add a second vendor if one is already wired.
- `src/telemetry/store.js` (or the repo's language equivalent): `increment(bucket, key)`, `get(bucket, key)`, `append(collection, record)`, `list(collection, sinceTs)`. One module, no ORM.
- An in-memory implementation of the same interface for tests.
- README "Deployment" note: which store, which env vars, what happens if they are unset (the endpoint must fail loudly, never silently no-op).

## Non-goals
- No schema migrations framework, no admin UI, no caching layer. No telemetry logic — that is S3-02.
- **The builder never provisions a paid vendor account, never writes Production or Preview environment variables, and never runs a production deploy.** Prepare the change and stop; the owner runs those three. (Added 2026-09-10 after a builder did all three unasked.)

## Acceptance criteria
0. **Any HTTP surface added to prove criterion 1 ships authenticated from its first deploy.** A shared-secret header, read from config, checked before any store call, failing CLOSED when the secret is unset (a misconfigured deploy refuses, it does not accept anonymous writes). Constant-time compare; the rejection body never echoes the expected value. An unauthenticated probe endpoint on a public deployment is a failed criterion, not a temporary state.

   **Ruled 2026-09-10, after the fact.** The original criterion 1 demanded proof against the real deployment and said nothing about how to expose it. The builder did the most direct thing that satisfied it and shipped two publicly writable endpoints to production. That is a spec defect, not a builder defect: anyone could inflate `runs_30d`, the number the day-90 scale-or-kill call reads, and write without limit into a paid Redis. Fixed in `agent-cost-calc` by commit `dd483e4`.

1. **Cold-start durability, proven against the real deployment, not a local process.** Deploy; call `increment` once; wait past the platform's idle window (or force a new deployment); call `get` from a fresh invocation and read back the incremented value. Commit the two timestamped responses and the deployment ids as evidence. A test that only exercises the in-memory implementation does not satisfy this criterion.
2. With the store env vars unset, the endpoint returns a 5xx with a message naming the missing variable, and does not return 200 with a zero count.
3. The in-memory and real implementations pass the same test file (one suite, two backends).
